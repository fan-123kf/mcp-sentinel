# 端到端对照实验报告（第四轮：网关 vs 直连，同环境同任务同模型）

**日期**: 2026-09-01
**实验目的**: 补齐三轮实验的最后缺口——在**唯一变量为工具暴露方式**的条件下，量化网关模式与静态注入模式的真实差异。
**原始数据**: `docs/eval\e2e_comparison.json`；子代理完整摘要与日志见 `hermes\cache\delegation\`（deleg_6f5582cf）。

---

## 1. 实验设计

| | 网关组 | 直连组 |
|---|---|---|
| 工具可见性 | 5 个元工具（576 tok 常驻） | **53 个工具全量 schema（7,614 tok）** |
| 发现方式 | search → invoke（先搜后调） | tools 清单 → 直接 call（免发现） |
| 执行路径 | **同一网关后端**（保证执行一致） | 同左 |
| 任务 | **完全相同的 6 项**（T1 读文件 / T2 echo / T3 目录计数 / T4 语义鸿沟-PR / T5 求和 / T6 文件大小） | 同左 |
| 模型 | glm-5.3-flash | 同左 |
| 隔离 | 每组一个全新上下文的子代理 | 同左 |

前轮已修复：filesystem 白名单加入 sandbox 目录（T1/T3/T6 上轮被环境阻断，本轮可完整走通）。

## 2. 核心结果

### 2.1 主指标对比

| 指标 | 网关组 | 直连组 | 差异 |
|------|--------|--------|------|
| **任务成功率** | **6/6** | **6/6** | 持平 |
| **静态工具 token/轮** | **576** | **7,614** | **网关省 92.4%** |
| 总耗时 | 153.9s | 100.5s | **网关慢 53%** |
| CLI 命令总数 | 11 | 6 | 网关多 5 |
| **LLM API 轮次** | **7** | **8** | **网关反而少 1** |
| 发现类调用 | 6 | 1 | 网关多 5 |
| 执行类调用 | 5 | 5 | 持平 |
| 参数/格式错误 | 1（backslash，自修复） | 1（同款，自修复） | 持平 |
| 错误工具调用 | **0** | **0** | 持平 |

> **API 轮次口径的洞察**：网关组 7 轮 < 直连组 8 轮——网关的额外成本不在对话轮数（CLI 把多次搜索合并进了单轮推理），而在单轮内的推理深度与串行等待。**"网关慢 53%"主要是墙钟时间，不是 API 账单轮次**。对按轮计费的场景，网关的发现成本比墙钟时间暗示的更便宜。

### 2.2 一句话结论

> **两者都能完成全部任务；网关用 53% 的时间换 92.4% 的 token 节省。代价集中在"发现"环节（多 5 次调用），执行环节两者完全一致（5 次调用持平）。**

## 3. 质性差异（数字看不到的部分）

### 3.1 直连组的"全量红利"（schema 完整可见的隐性优势）

1. **T3→T6 联动**：直连组在 T3 选了 `list_directory_with_sizes`（而非 plain `list_directory`），**顺带拿到文件大小，T6 不用再查**——因为它能看到 schema 里 "also reports sizes" 的细节。网关组搜索结果里没有这层信息，T6 单独花了一次搜索+调用
2. **T4 零成本**：直连组 0 次调用，直接扫描工具清单得出 `github__create_pull_request`。网关组靠把"pull request"预混进查询词一次命中——**如果它没想到预混，就会重演第三轮的多步迭代**
3. **T6 双重交叉验证**：直连组用两个工具互相印证答案（62 bytes），网关组单工具单路径

### 3.2 网关组的真实弯路（TF-IDF 弱点在对照中的定位）

T3 的轨迹：`"list directory contents"` → **返回的全是 GitHub 工具**（"directory"词撞上 github repo 语义）→ `"list allowed directory files folder"` 仍未命中 → 第 3 次改词 `"list directory tree files in a folder local filesystem"` 才找到 `directory_tree`。

**这正是第二轮"跨 server 干扰"缺陷在真实链路的形态**：多 server 场景下，词法匹配会被其他 server 的工具淹没。直连组不存在这个问题——它直接看到 filesystem server 下所有工具的名字空间。

### 3.3 两组共同的行为模式（变量控制成功的证据）

- 两组都在 T1 遇到同样的 backslash JSON 转义问题，都改用正斜杠自愈——证明环境变量被良好控制
- 两组都没有任何一次错误工具调用——第三轮"LLM 兜底有效"的结论在直连组同样成立

## 4. 成本模型的最终形态

结合四轮实验，网关模式的完整账本：

| 成本项 | 网关 | 直连 |
|--------|------|------|
| 每轮常驻 token | **576** | 7,614 |
| 发现成本/任务 | ~2 次搜索（约 15-30s LLM 时间） | 0 |
| 顺带信息红利 | 无（描述一行） | 有（完整 schema） |
| 规模敏感性 | 工具↑→搜索质量↓（R@1 33% 且随规模恶化） | 工具↑→token 线性↑，且 LLM 选择难度↑ |
| 健康治理/审计 | **有** | 无 |

**盈亏平衡点估算**（本次实验数据外推）：
- 6 任务场景：网关多花 ~53s（≈ 3-5 次 LLM 轮次），省 7,038 tok/轮。**对话轮数 >2 时网关开始回本**（省的静态 token 超过多花的轮次成本）
- 但回本的前提是**搜索命中质量不随规模坍塌**——53 工具时 R@1=33%，300 工具时若无 embedding，发现次数会膨胀，53% 的时间差会扩大到侵蚀 token 收益

## 5. 四轮实验总裁定（最终版）

| 维度 | 裁定 | 证据轮次 |
|------|------|---------|
| token 经济性 | ✅ 92.4% 实测，规模越大越有利 | 第二轮（tiktoken） |
| 健康闭环 | ✅ 全项目最扎实功能 | 第二轮（降级→剔除实证） |
| 治理管控 | ⚠️ move_file 漏拦，关键词表不完整 | 第二轮 |
| 检索质量 | ❌ R@1=33%，跨 server 干扰实测复现 | 第二、四轮 |
| LLM 纠错对冲 | ✅ 弱检索可被强模型架构性补偿 | 第三、四轮 |
| **端到端等价性** | ✅ **6/6 = 6/6，正确性无差异** | **本轮** |
| **端到端效率** | ⚠️ **+53% 时间换 -92.4% token** | **本轮** |

**最终定性（四轮闭环后）**：

> mcp-sentinel 是一个**用时间换 token、用搜索换上下文**的架构交易。它在正确性上无损（两组 6/6 持平、0 错误调用），在成本上是一次明确的再平衡——常驻 context 降 92.4%，每次任务多 2-3 次发现调用。**这个交易在"工具多、对话长、模型强"的场景下是赚的；在"工具少、对话短、模型弱"的场景下是亏的**。而它独有的健康治理与审计，是直连模式无论如何给不了的部分——这才是它存在的根本理由，token 节省只是顺带。

## 6. 实验局限

- 6 任务样本，统计意义有限；结论方向可信，比例数字仅供参考
- 直连组的"直连 CLI"仍经由网关转发执行（为保证执行路径一致）——真实直连场景下执行延迟会略低，但不影响发现成本对比的结论
- 未测 300+ 工具规模（预期网关发现成本将非线性上升，是 embedding 决策的关键输入）
- 两组子代理均可读 workdir 文件，存在轻微的"环境探察"噪声（第三轮已观察到）
