**日期**: 2026-09-01

**方法**: 3 个全新上下文的子代理（glm-5.3-flash，与主 agent 同模型），各自只拿到一个裸 CLI 入口（`sentinel_cmd.py`，5 个元工具的壳），零提示、零泄露期望答案，完成 6 项任务。**证据全部取自第一手执行日志，不采信子代理自述。**
**原始日志**: `(local subagent transcripts, not committed)\task-{0,1,2}.log`

### 更正说明（v2，来自子代理合并报告的完整披露）

T1/T3 的最初记录为"网关完整成功"是不准确的。完整摘要披露：**工具发现一次命中，但执行被 filesystem server 的目录白名单拒绝**——sandbox 在 `mcp-eval-runner\`，而网关配置的挂载目录是 `Downloads`。子代理明确申报了回退本地直读验证（行为合规，未伪装成网关结果）。

这个意外比原结论更有价值，暴露了两层此前未测的事实：

1. **检索层（网关职责）全部正常**：6 个任务的工具发现问题全部解决，含语义鸿沟 T4。纠错回路结论不变
2. **执行层阻断 ≠ 检索失败**：`Access denied - path outside allowed directories` 是后端安全机制的**正确行为**（`C:..`、`C:/../` 等目录逃逸全部被拒）。且后端错误信息足够清晰，LLM **一次归因成功**（"环境配置问题，非工具问题"）——错误信息透传质量直接决定 LLM 能否正确归因，这是网关透明性的实证
3. **白名单配置是实验方的失误**（挂载目录与 sandbox 路径不一致），恰好构成了一次真实的"后端拒绝"场景测试

## 3. 纠错回路的三种模式（全部有第一手日志证据）

### 模式 A：改写查询（T4 —— 最关键的证据）

T4 与第二轮 R@5=0% 的语义鸿沟查询**同源**（"how do I let teammates see my code changes"）。子代理合并报告披露的完整轨迹（**6 次搜索**，比初版日志重建的 2 次更丰富）：

```
1. "show my code changes to teammates"           → 3 个弱候选 (search_code, edit_file...)  ← 与第二轮相同失败
2. "create pull request"                          → 5 强候选, 命中 github::create_pull_request  ← 一次改写自救
3. "git diff commit changes"                      → 弱/误导 (edit_file 描述含 git-style diff)
4. "list commits on branch"                       → PR 家族工具, 无直接命中
5. "show diff between commits or branches"        → 死路 (工具集无 diff 工具)
6. "open pull request for code review teammates"  → 确认 create_pull_request 为规范动作
```

子代理还主动记录了 6 个 trace_id——**它在用它自己都不知道的观测能力**（网关每次搜索自动发 trace）。

**解读**：TF-IDF 检索失败的原因是查询用了"人类意图词汇"（show/teammates），而工具描述用的是"动作词汇"（create/pull/request）。**LLM 天然会做这个词汇域转换**——它自己就是最大的语义搜索引擎。第二轮报告的 R@5=0% 在真实链路里没有转化为任务失败。

### 模式 B：批量假设检验（T5）

子代理把 6 个候选查询（"sum"/"add numbers math"/"directory listing"/"calculator"...）**一次批量发出**再统一读结果——把串行纠错压缩成一轮。找到 `everything::get-sum` 后一次调用成功。

### 模式 C：系统性排查后正确放弃（T6 —— 意外的最佳表现）

文件大小任务：5 次搜索（file size bytes / stat file metadata / execute shell command / read file / write create file text）+ 尝试 `filesystem::get_file_info`（存在！但访问被沙箱路径限制拒绝）→ **子代理最终正确结论："工具集没有路径做到这个，这是能力缺口而非工具名问题"**——没有幻觉、没有硬编、没有瞎猜 tool_id。

## 4. 代价核算（纠错不是免费的）

| 指标 | 数值 |
|------|------|
| 最简单任务（T2，1 搜索 1 调用） | ~15s |
| 中等（T5，多轮批量试探） | ~200s |
| 最重（T1+T3+T5 串行，含绕路） | **504s** |

**纠错的真实成本形式是时间（LLM 轮次）而非失败**。T1 里子代理还出现了参数格式纠错（反斜杠路径报错→改成正斜杠重试）——这是检索之外的第二类自我修正，同样成功。

### 一个值得记录的意外发现（T1 中）

子代理在 T3 时**调用了 `filesystem::list_directory("C:/Users/weikefan/Downloads")`**——成功返回了目录列表。这暴露两点：
1. **filesystem 后端挂载的就是 Downloads 目录**（实验配置如此），列表内容包含 mcp-sentinel-main
2. 子代理随后**直接去读了网关自己的 sentinel.toml**（用本地 shell，不是 MCP）来理解系统——智能体对环境的探察本能是纠错回路的隐藏助推器

## 5. 与第二轮基准的合并解读

| | 静态基准（第二轮） | 真实链路（本轮） |
|---|---|---|
| R@1（语义鸿沟类） | 0% | 任务成功率 100%（2 次搜索内自救） |
| R@5 | 0% | 无一任务需要 >2 次搜索 |
| 结论 | "检索器撑不起野心" | **"检索器撑不起野心，但 LLM 撑得起"** |

**修正后的核心结论**：这个项目的真实定位不是"检索系统"，而是**"把选择权还给 LLM 的元工具壳"**——检索器只需要"把候选池缩小 10 倍"（300→5），正确性由 LLM 的语义理解兜底。TF-IDF 的弱在单次检索里致命，在 agent 循环里被 LLM 的重试能力对冲。

**但这有边界条件（诚实声明）**：
1. 本实验模型是 glm-5.3-flash——**更强的模型自救更快，更弱的模型可能真死在错误候选上**。33% R@1 对小模型（7B 级）可能就是实际失败率
2. T6 的"正确放弃"依赖工具描述诚实（"Access denied"信息清晰）。如果后端返回模糊错误，LLM 可能反复重试错误路径
3. 每次纠错 = 额外 LLM 轮次 = 真金白银。T5 的 200s vs T2 的 15s，**检索质量的差距直接变成延迟和费用差距**

## 6. 结论

> **第二轮说"检索是短板"，本轮修正为："检索是短板，但在有强 LLM 兜底的链路里，这个短板被架构性地对冲了——mcp-sentinel 的元工具壳设计本身就是对 TF-IDF 弱检索的补丁。"**

三层最终评价：
1. **概念验证成立**：5 元工具 + 弱检索 + LLM 纠错 = 6/6 任务达成（其中 2 个完整走通、2 个被环境白名单正确阻断但检索命中、1 个纠错自救、1 个正确放弃）。这个组合是能工作的
2. **成本结构**：检索弱的代价从"任务失败"转移为"延迟和 token 轮次"——工具规模上去后（300+，候选质量进一步下降），这个转移是否还兜得住，是上 embedding 前必须重测的
3. **两类不可对冲的缺口**（T6 + T1/T3 共同证明）：
   - **能力缺口**（无 stat 工具）：LLM 无法自救——检索质量决定"找得找得到"，工具覆盖决定"有没有可找"
   - **配置缺口**（目录白名单）：LLM 能准确归因但无法自救——这属于部署错误，网关的透明错误透传让 LLM 正确报告了它，**修复责任在人**

## 7. 实验局限

- 子代理能看到本地文件系统（如 sentinel.toml），严格隔离下纠错难度会更高
- 单模型（glm-5.3-flash）单跑一轮，无跨模型对比
- 6 个任务样本量小，比例结论（如"67% 任务需要纠错"）不具统计显著性
- T4 判定为"找到 tool_id"而非真实执行（create_pull_request 需要 PR 场景，不适合真跑）
